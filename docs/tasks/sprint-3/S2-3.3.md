# Persist nutrition goals

## Description

Serves S2-3 by saving the nutrition goals validated in S2-3.2, so they are still there the next time a student opens the Nutrition goals screen. This task also covers S2-3.4: unit tests for persistence. Validation tests already exist from S2-3.2.

Goals are stored on the device with AsyncStorage, the same way S2-4.1 stores food preferences. Supabase storage is out of scope. The mobile app has no Supabase client or sign-in yet, and every user-owned table in this project requires `auth.uid()` through row-level security. Syncing goals to Supabase can follow once the app has accounts.

Out of scope:

- Showing goals or progress on the Home screen or in the daily log.
- Syncing goals across devices or to Supabase.

## Specs

- Add a storage module at `apps/mobile/src/features/nutrition-goals/storage-core.ts` with no React or React Native imports.
  - `createNutritionGoalsStorage(storage)` takes any `KeyValueStorage` (`getItem`, `setItem`) and returns `{ loadNutritionGoals, saveNutritionGoals }`.
  - The storage key is versioned: `@app:nutrition_goals_v1`.
  - The stored value is JSON: `{ goals: { calories, protein, carbs, fat }, updatedAt }`. Each goal is a number or `null`, and `updatedAt` is an ISO 8601 UTC timestamp.
- `loadNutritionGoals()` returns `{ goals, updatedAt }`:
  - With nothing saved, it returns every goal as `null` and `updatedAt: ''`.
  - Malformed JSON, or a value that is not an object, also returns those defaults.
  - Each stored goal is checked separately. A goal that is missing, not a number, negative, not finite, or a non-whole calories value becomes `null`. Valid goals from the same record are kept.
  - An invalid `updatedAt` becomes `''`.
  - Storage read errors are thrown, so the screen can show them.
- `saveNutritionGoals(goals)` writes the goals with a new `updatedAt` and returns what it wrote.
  - It checks the goals with the same rules as loading. If any goal is invalid, it throws a `RangeError` and writes nothing. Bad data is never silently dropped.
  - Saving every goal as `null` is valid and clears all goals.
  - It does not change its input.
  - Storage write errors are thrown.
- `goalsToInputState(goals)` converts saved goals back to form strings: numbers become their string form (`85.5` becomes `"85.5"`), and `null` becomes `""`.
- `apps/mobile/src/features/nutrition-goals/storage.ts` binds the core to AsyncStorage and exports `loadNutritionGoals` and `saveNutritionGoals`.
- Screen behavior in `nutrition-goals-screen.tsx`:
  - The screen takes `loadGoals` and `saveGoals` props instead of `onSave`. The route passes in the AsyncStorage functions.
  - On open, it shows a loading state, then fills the form with the saved goals. Unset goals stay blank and show their placeholders.
  - If loading fails, it shows an error with a "Try again" action. The form is not shown, so a student can't overwrite goals they can't see.
  - Save goals still validates first, as in S2-3.2. Invalid fields block saving.
  - While saving, the Save button shows a spinner and is disabled.
  - After saving, the form shows the saved values in normal form, for example ` 007 ` becomes `7`. The screen shows "Goals saved on this device."
  - If saving fails, it shows "Could not save your goals. Please try again." The values the student entered stay in the form.
  - Editing any field clears the saved and save-error messages.
  - Status and error messages are exposed to screen readers.

## Requirements

- No new runtime dependencies. `@react-native-async-storage/async-storage` is already installed.
- No changes to the API, database, or scraper.
- Keep validation rules in `validation.ts` and field definitions in `NUTRITION_GOAL_FIELDS`.
- Existing tests must keep passing.
- `npm test`, `npm run lint`, and `npx tsc --noEmit` pass in `apps/mobile`.

## Acceptance criteria

1. Saving goals, leaving the screen, and coming back shows the same values.
2. Saved goals are still there after the app restarts.
3. Fields saved as blank reopen blank and show their placeholders.
4. Saving with every field blank clears previously saved goals.
5. Invalid input still blocks saving and leaves the stored goals unchanged.
6. A storage read failure shows an error with a retry action. A storage write failure shows a save error and keeps the student's input.
7. Corrupted or partly invalid stored data never crashes the screen. Invalid goals load as blank, and valid ones are kept.

## Tests (S2-3.4)

- `node:test` unit tests in `apps/mobile/src/features/nutrition-goals/storage.test.ts`, run with `tsx` through `npm run test:nutrition-goals`, using an in-memory `KeyValueStorage`:
  - Defaults when nothing is saved.
  - Save then load round trip, including `null` goals, decimals, and `0`, using the versioned key.
  - Saving every goal as `null` clears earlier goals.
  - `updatedAt` is a valid ISO timestamp.
  - Malformed JSON, non-object JSON, and per-field invalid stored values: wrong type, negative, decimal calories, and missing fields.
  - `saveNutritionGoals` rejects invalid goals, writes nothing, and does not change its input.
  - Read and write errors are thrown.
  - `goalsToInputState` turns stored goals into form strings, and those strings pass `validateNutritionGoals` back to the same goals.
