# Store reusable meal playlists

## Description

Serves S3-3 by creating persistent Supabase storage for named meal playlists and their food items. Playlist screens, API endpoints, and nutritional totals are outside this task.

## Specs

- The `public.meal_playlists` table stores a generated ID, owner ID, nonblank name, and creation time.
- The `public.meal_playlist_items` table stores a generated ID, playlist ID, food name, positive serving quantity, and optional nonnegative calories, protein, carbohydrate, and fat values per serving.
- Items retain their food and nutrition snapshot when the scraped food database is replaced. Deleting a playlist also deletes its items.
- Authenticated users can create, read, update, and delete their own playlists and items. They cannot access another user's playlists or items.
- Database tests exercise these tables and policies against local Supabase.

## Requirements

- Add a Supabase migration and use the existing local Supabase test environment.
- Associate each playlist with an existing Supabase Auth user and enable row-level security on both tables.
- Preserve existing food tables and scraper behavior.
- Keep the service role key on the server and out of committed files.

## Acceptance criteria

1. An authenticated user can create a named playlist, add an item with a positive serving quantity, and retrieve both after reconnecting.
2. Blank playlist names, nonpositive serving quantities, and negative nutrition values are rejected.
3. A second authenticated user cannot read or modify the first user's playlist or its items.
4. Deleting a playlist removes its items, and replacing food database rows does not remove saved items.
