# Save and retrieve daily food log entries

## Description

Serves S3-1 by providing persistent storage and API access for daily food log entries. Sign-in, log screens, editing and removal, and daily totals are outside this task.

## Specs

- `public.daily_log_entries` stores an owner, food name, optional nutrition values per serving, positive serving quantity, consumption date, and creation time. Food details are snapshots so menu refreshes cannot delete logged entries.
- `POST /api/log-entries` accepts a food name, serving quantity, consumption date, and optional per-serving calories, protein, carbohydrate, and fat values. It returns the saved entry.
- `GET /api/log-entries?date=YYYY-MM-DD` returns the authenticated user's entries for that date.
- Both endpoints require a valid Supabase Auth bearer token. Entries are isolated by owner using row-level security.
- Blank names, invalid dates, nonpositive quantities, and negative or nonnumeric nutrition values are rejected.

## Requirements

- Add a Supabase migration without changing the existing food tables or scraper.
- Preserve unknown nutrition values as null and retain true zero values.
- Use the local Supabase stack for integration tests. No service-role credential is exposed to the client.
- The app currently has no sign-in; integrating it with this API is future work.

## Acceptance criteria

1. An authenticated user can save an entry and retrieve its food, quantity, date, and nutrition values after reconnecting.
2. Invalid food names, quantities, dates, and nutrition values receive a client error and are not saved.
3. Missing or invalid authentication is rejected and another user cannot read the saved entry.
4. An entry remains available after a food database row is deleted, and unknown and zero nutrition values remain distinct.
